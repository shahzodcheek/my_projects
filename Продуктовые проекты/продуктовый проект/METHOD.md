# Методика расчёта REES46

## Источник и паспорт

Использованы два архива издателя из раздела «Поведение посетителей магазина косметики». В разделе Marketplace у издателя есть файлы с теми же именами. Версию для косметики подтверждают путь `/datasets/cosmetics/`, соответствующая ссылка на Kaggle и заголовок из девяти полей. Размер, SHA-256 загруженных байтов, период и проверки по каждому файлу приведены в паспорте. [Страница издателя](https://data.rees46.com/) · [Описание на Kaggle](https://www.kaggle.com/datasets/mkechinov/ecommerce-events-history-in-cosmetics-shop) · [Паспорт](aggregates/data_passport.csv)

| Колонка исходного CSV | Что означает и как используется |
|---|---|
| `event_time` | Строка UTC с точностью до секунды. Для расчёта разбирается в метку времени UTC и проверяется на принадлежность месяцу файла. |
| `event_type` | Событие. Для расчёта используются `cart`, `purchase` и `remove_from_cart`. Просмотры учитываются в паспорте и проверке покрытия. |
| `product_id` | Ключ товара, положительное целое. |
| `category_id` | Ключ категории, положительное целое. Для сегментации берётся с первой подходящей строки `cart`. |
| `category_code` | Текстовый код категории. Пустое значение отражается отдельно. |
| `brand` | Текстовая марка. Пропуски отражены в паспорте. |
| `price` | Число в журнале на момент `cart`. Нулевые значения сохраняются и считаются отдельно. Отрицательное, нечисловое или выходящее за формат точности значение относится к неизвестным. |
| `user_id` | Ключ пользователя, положительное целое. |
| `user_session` | Строковый ключ сессии. Пробельные края удаляются, пустые строки превращаются в неизвестные значения. |

Журнал содержит события магазина. Шаги оформления, плата и срок доставки, промокоды, ошибки оплаты, причины паузы и покупки у другого продавца в этой схеме отсутствуют.

## Когорта и фильтры

1. Из октябрьских `cart` исключаем записи без корректной октябрьской метки UTC, затем записи без положительных целых `user_id` и `product_id`. Те же проверки применяются к связанным событиям по соответствующему месяцу файла.
2. Внутри каждого файла схлопываем точные дубли по всем девяти исходным полям, сохраняем первую CSV-запись. Строки с одинаковой секундой и разными полями считаются разными событиями.
3. Для каждого кандидата проверяем, что `t0 + 7 дней` не позже последнего фактического события и на всех UTC-датах окна были события. Это проверка покрытия лога по датам. При запуске только с октябрём последнее возможное включение ограничено верхней границей конца октября с вычетом семи дней.
4. В каждой паре «пользователь × товар» оставляем первое подходящее добавление. При одинаковой метке выбираем первую из подходящих записей по порядку в CSV. Повторные добавления не открывают новое окно. Основной интервал `(t0, t0 + 7 дней]`. Вариант с `[t0, t0 + 7 дней]` проверяется отдельно.
5. Для чувствительности к длине окна считаем долю купивших тот же товар на `(t0, t0 + 24 часа]` на той же когорте. Цена и категория привязаны к стартовому добавлению, поэтому знаменатели для двух окон совпадают. Сегменты цены задаются одинаковыми границами для всей когорты.

## Метрики

| Метрика | Числитель | Знаменатель |
|---|---|---|
| Тот же товар за 7 дней | Пары, у которых найден хотя бы один `purchase` того же товара тем же пользователем в основном окне | Все пары когорты |
| Тот же товар за 24 часа | Пары с такой покупкой в первые 24 часа | Все пары когорты |
| Тот же товар за 7 дней с учётом `t0` | Пары с такой покупкой в окне, включающем секунду добавления | Все пары когорты |
| Покупка точно в `t0` | Пары с такой покупкой в секунду добавления | Все пары когорты |
| Покупка в той же сессии | Пары хотя бы с одним `purchase` того же товара в основном окне и сессией, равной сессии добавления | Пары с известной сессией добавления |
| Покупка в другой сессии | Пары хотя бы с одним `purchase` того же товара в основном окне и известной сессией, отличной от сессии добавления | Пары с известной сессией добавления |
| Неизвестна сессия покупки | Пары хотя бы с одним `purchase` того же товара в основном окне и пустой сессией покупки | Пары с известной сессией добавления |
| Неизвестна сессия добавления | Пары с пустой сессией добавления, где был `purchase` того же товара в основном окне | Пары с неизвестной сессией добавления |
| Покупка другого товара | Пары, после старта которых у того же пользователя был хотя бы один `purchase` другого товара в основном окне | Все пары когорты |
| Удаление товара | Пары хотя бы с одним `remove_from_cart` того же товара тем же пользователем в основном окне | Все пары когорты |

Флаги событий могут одновременно срабатывать на одной паре, включая покупку в той же и в другой сессии. Покупка другого товара может быть учтена для нескольких пар одного пользователя. Пустая сессия покупки даёт вклад в общую конверсию, её принадлежность к стартовой сессии неизвестна. При неизвестной стартовой сессии общее наличие покупки определяется по паре. Удаление является наблюдаемым событием, товар могли затем добавить снова и купить. [Метрики](aggregates/metrics.csv) · [Пересечения](aggregates/intersections.csv)

## Воспроизведение

Из корня кейса, с Python 3.11 или новее. Архивы можно сохранить в `/tmp/rees46-cosmetics` или передать существующие `.csv.gz` и `.csv` через соответствующие аргументы.

```bash
mkdir -p /tmp/rees46-cosmetics
curl -fL https://data.rees46.com/datasets/cosmetics/2019-Oct.csv.gz -o /tmp/rees46-cosmetics/2019-Oct.csv.gz
curl -fL https://data.rees46.com/datasets/cosmetics/2019-Nov.csv.gz -o /tmp/rees46-cosmetics/2019-Nov.csv.gz
python -m venv .venv
. .venv/bin/activate
python -m pip install -r quant/requirements.txt
python quant/run.py --october /tmp/rees46-cosmetics/2019-Oct.csv.gz \
  --november /tmp/rees46-cosmetics/2019-Nov.csv.gz
```

Аргумент `--november` можно опустить для расчёта на укороченной когорте. Скрипт проверяет заголовки CSV и сохраняет агрегаты в `quant/aggregates/`. Excel строится из тех же результатов. Скрипт сверяет числители, знаменатели, суммы групп, согласованность окон и пересечения, а затем перечитывает контрольные ячейки записанного Excel.
